# Historical H6 XNU RAM transport

These files preserve the N986B H6 host-side **format, transfer plan, and offline Upload A/B checks**. H6 was a volatile-RAM, read-only diagnostic. Its observed result was two 512-byte pre-root block-vnode strategy reads from a 1 MiB high-RAM fixture, with zero writes. It did **not** mount a filesystem, boot iOS userspace, or show an iOS UI.

## What is included

- `h6_manifest.py`: validates the exact historical FD, callback stage, ARM64 XNU Mach-O, and 1 MiB fixture pins; constructs the 4 KiB v3 manifest and 51,712-frame low stream. It performs no device I/O. Its output files are optional and created exclusively.
- `h6_send_plan.py`: reconstructs the nine setup OUTs, 64-byte `SET_SEL` control payload hashes, 2,048 high frames, 51,712 low frames, and one terminal operation. It only prints a plan. It never opens USB.
- `verify_h6_upload_ab.py`: checks twelve already-collected A/B pairs against the exact H6 inputs, same-session manifest tag/receipt, UEFI marker and snapshot, XNU scratch commit, and ordered H4/H5/H6 console markers. It only reads local files. The collector that originally obtained those files is described in [H6-LIVE-REFERENCE.md](H6-LIVE-REFERENCE.md); it is not bundled.

## Dependencies and inputs

The three included programs require **Python 3.10+ and only the Python standard library**. They run on Windows, Linux, or macOS. The historical live USB sender used `libusb-1.0`, PyUSB for device enumeration, a device-specific callback stage, a fresh Android state receipt, and prior H3/H4b/H5 independent A/B gates. The original bounded Upload reader was a native `libusb-1.0` program. Neither live USB program is included here.

## Fixed H6 layout

| Region | Physical address | Length or count |
| --- | ---: | ---: |
| callback stage | `0x8b000000` | 340 bytes; state at `0x8b000200` |
| UEFI FD | `0x90000000` | `0x700000` bytes |
| v3 manifest | `0x90700000` | 4,096 bytes |
| ARM64 XNU Mach-O | `0x90701000` | 19,057,760 bytes |
| low stream end / terminal address | `0x91940000` | 51,712 × 512-byte frames, then one 8-byte `UEFITERM` |
| high-RAM witness | `0x940000000` | 2,048 × 512-byte frames |
| XNU scratch | `0x940100000` | 4,096 bytes |
| UEFI handoff snapshot | `0x95d00000` | 4,096 bytes |
| UEFI loader marker | `0x95e00000` | 4,096 bytes |

The low stream is FD + manifest + Mach-O + zero padding to the exclusive end address. The v3 manifest header uses `<8sIIQQQ32s256sIQQ32s`; its read-only store record uses `<8sHHIQQII32sQ`. Its 64-bit session tag is the first eight seed bytes in little-endian order. A newly generated seed changes the manifest and low-stream hashes; the exact historical preview hashes were `9e207a35264ba2b5fd41e166f6646005772d697c10517055bb5dd690cda23d6c` (manifest) and `7041f31c4902d02c7e8c320619688c0f61106334fff00b407d0aed478596fc71` (low stream). These preview hashes are cross-checks only, not fresh-session targets.

## Offline use

Run the tools from this directory, passing **local** paths for inputs:

```text
python h6_send_plan.py --stage path/to/stage.bin
python h6_manifest.py --fd path/to/UEFI.fd --stage path/to/stage.bin --kernel path/to/xnu-macho --witness path/to/witness.bin --seed path/to/private-seed.bin
python verify_h6_upload_ab.py --dump-dir path/to/captured-upload-pairs --send-receipt path/to/send-receipt.json --fd path/to/UEFI.fd --stage path/to/stage.bin --kernel path/to/xnu-macho --witness path/to/witness.bin
```

`h6_manifest.py` prints hashes by default. `--manifest-output` and `--low-output` optionally write the generated bytes to new paths. Keep generated images, seed, receipts and raw RAM dumps outside the repository. The verifier expects files such as `manifest-A.bin` and `manifest-B.bin`; the full twelve-pair list is in its `REGIONS` constant.

## Replay boundary

The shipped code can reconstruct and verify the **host byte format** when the exact pinned inputs are available. It cannot transmit to the phone or collect Upload RAM. A new live attempt needs an independently reviewed USB sender, an independent bounded Upload reader, current device identity and boot-state checks, same-run receipt binding, and safe handling of an uncertain terminal disconnect. The terminal was attempted once; a disconnect must be resolved from Upload A/B evidence, never by blind retry.

The published offline verifier checks the contents of files provided to it. It cannot prove their physical origin, collection time, or whether the same handset produced them. The historical live collector had additional device identity, reader hash, symbol, timestamp, and prior-gate checks which are intentionally absent here. Do not describe an offline pass as a new device result.

**Validation of these curated scripts:** syntax compiled; the manifest generator reproduced the historical preview manifest and low-stream SHA-256 values; the offline verifier passed against the retained historical H6 A/B set (12 pairs, 22 ordered markers, two reads, zero writes). These modified scripts were **not tested on a device**.
